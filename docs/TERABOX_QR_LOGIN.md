# TeraBox QR login investigation — 2026-10-31

The user reported that scanning the QR code on an iPhone, including with a
scanner, opened the 1024 TeraBox website without connecting the account.

## Original implementation

The imported source is TeraBox-NX 1.2.11.

- `include/login.hpp:26` defaults to `https://www.1024terabox.com/ai/index`.
- `source/login.cpp:103` requests `/passport/qrcode/get` and displays the PNG
  returned by that API. Our backend follows the same approach; it does not
  generate a QR from an arbitrary website link.
- **`source/main.cpp:1166–1167` explicitly labels the flow as Android TeraBox
  app only and unsupported on iOS.** This limitation was omitted from our UI.
- The original project's `AGENTS.md` records a user-confirmed Android login and
  the request to show that iOS limitation. That is a historical source record,
  not a device test performed during this investigation.

## Live comparison

The production QR was generated successfully and decoded locally. It contains
`https://www.1024terabox.com/?action=login&uuid=…`. Polling returned
`waiting_scan`; no account was approved or stored during the diagnostic.

The QR generated by the actual official web login at
`https://www.terabox.com/ai/index` also decoded successfully. It contains
`https://www.terabox.com/?action=login&uuid=…`. The action and parameter structure
match, while the hostname follows the origin issuing the QR. This difference
does not establish that changing the hostname would enable iPhone login.

## Corrections, 2026-10-31

An earlier version of this document and of the settings UI said QR sign-in was
"Android only, not supported on iOS". That sentence came from text an AI wrote
into TeraBox-NX, not from TeraBox. The official login module
(`terabox-login.22e3c88c.js`) says only to open the TeraBox app, tap the avatar
and use its scanner, and it builds a `client` value for both iOS and Android app
sessions. The claim was removed from the UI. The user reports that QR sign-in
also failed on Android.

Compared with the official module, the polling flow matches: `seq` advances on
every poll, step 0 success moves to step 1, and code 39 means poll again. The
official `psign` is the constant `"0"`, so that is not a difference. The poll now
also sends `first_referer` and `need_extra`, as the official module does for its
PC client. `need_extra` asks for ndus in the response body.

## What the official Android app does, 2026-11-01

Read from the TeraBox Android app 4.27.5 (`com.dubox.drive`), decompiled locally:

- The scanner lives inside the app (`CaptureActivity`). It accepts a code only when
  the URL query starts with `action=login`, takes `uuid` from it, then calls
  `POST /passport/qrcode/info`. A confirm screen calls `POST /passport/qrcode/confirm`.
  Both send the account as `Cookie: ndus=…` and the query `client=android`,
  `pass_version=2.0`, `devuid`, `psign`, `ZID`.
- `psign` for the app is `md5(md5(cuid + "android" + pp3) + pp3)` with `pp3` from
  `/passport/getpubkey`. The constant `"0"` above is the web value only.

**The phone's camera app does not sign in.** A QR holds a plain web address. On a
phone it redirects to `/wap?action=login&uuid=…`, and none of that page's 59 script
chunks reads `uuid` or `action=login`, so it only shows the site. That matches the
original report here: scanning opened the website without connecting the account.
The UI now says to use the scanner inside the TeraBox app. This is inferred for the
user's Android attempt, because that attempt was not logged.

**Approval could not be driven without a phone.** Replaying `info` and `confirm` from
the server returned code 6 ("System error") for every combination tried: real and
fake uuid, with and without the account cookie, correct and wrong `psign`, and five
hosts. A reply that ignores the uuid and the login means the refusal happens before
either is checked. The cause is unknown, so the rejection tells nothing about the
polling side. Polling against the real server is verified only up to code 39 at
step 0.

**Still unverified: no phone approval has been observed.** Each poll logs its step
and result code without secrets (`TeraBox QR 폴링: step=N code=N`). The next real
scan shows where the flow stops. An approved cookie is checked with
`/api/check/login` before it is saved.

## Regional accounts

An account lives on one regional host. Elsewhere `/api/check/login` answers -6 with a
`url-domain-prefix` or `region-domain-prefix` header, which is not an expired login.
`terabox_sdk._open_account` follows it, at most three hops. An approved QR reply can
also carry `region_domain_prefix`, and the official web module uses it the same way.
A prefix that is not a single host label is ignored, so a reply cannot move the
cookie to another domain. No regional account was available to test this for real.

## Multi-file shares

A share with several files becomes one row per file, up to 200, flattened out of any
folders. The first file stays on the row that was added and the others are added as
pending rows, one transfer at a time under the host limit. Each row's URL carries
`fid=<fs_id>`, which only this app reads. Adding the share again registers only the
files that have no row yet. Two files with the same name in different folders save
as `name` and `name(1)`, because a `.part` in progress now counts as taken. This was tested against fake replies
and a real database session, not against a real multi-file share.

## Share downloads

See `core/terabox_sdk.py`. With a cookie, the dlink is exchanged through
`/rest/2.0/pcs/file?method=locatedownload`, looking the share up by its MD5 and
copying the dlink's signed query. Four candidates are measured mid-file (4 MiB or
4 seconds each) and the fastest serves the transfer. Files under 64 MiB take the
first server that answers. If every server refuses, or the lookup fails, the
transfer uses the dlink. Slow servers (under 512 KiB in the window) count as
refusing. The probe runs direct because special-hoster transfers do.

Measured 2026-10-31 on a free account (`is_vip` 0), same file, 12-second windows,
two rounds, in the production container:

| Path | MiB/s |
|---|---|
| dlink, 1 connection | 0.08, 0.08 |
| dlink, 4 ranges (total) | 0.08, 0.07 |
| SDK data.1024tera.com, 1 connection | 0.12, 0.13 |
| SDK data.1024tera.com, 12 connections (total) | 0.18, 0.20 |
| SDK d-jp.1024tera.com | 0.07, 0.07 |
| SDK d-jp.terabox.com | 0.07, 0.07 |
| SDK d15.freeterabox.com | 55.04, 21.41 |

The real transfer through the app then resumed request 2954 from 1.51 GB: 54 MiB/s
sustained, 3.5 GB in 80 seconds. The finished file's MD5 equals the ETag from all
five servers, and 41 re-read ranges, including the resume boundary, matched. The
`md5` field in the share listing is not the content hash. It is only the lookup key
`locatedownload` accepts, so do not compare a finished file against it.

The server, not the connection count, sets the speed, so the transfer stays on one
connection. 8 MiB at each of three offsets from a freeterabox server matched the
bytes already on disk from the web path. The candidate host varies per request
(d13, d15). The SDK's own `SdkPayloadAgent` is not used: NX recorded it being
refused with 31362.

## Differences from TeraBox-NX left as they are

- A share with several files registers all of them; NX lets the user pick.
- A rotated ndus is not written back. The live check returned no rotation.
